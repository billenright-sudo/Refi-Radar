# Subscription billing: decisions made during the build

Every call the build coordinator made on Bill's behalf while building feature/billing (2026-11-05), in order, each with what it costs if wrong. Bill can reverse any of them.

- | T2 self | "a failed send retries next event" vs "confirm when the org's first subscription starts" | ambiguity → Ruling 2 |
- Ruling 1: Task 2 creates `syncSeats(db, gateway, orgId)` in server/lib/billing/seats.js (its sync_seats follow-up needs it); Task 3 only consumes it — the plan listed it under both — cost if wrong: none (one definition).
- Ruling 2: the `confirm` follow-up is emitted for any applied subscription event while `billing_confirmation_sent = 0` and the status is trialing or active, so a failed send is retried on the next event — cost if wrong: a confirmation could arrive a little after the trial actually began.
- Ruling 3: build continues straight from Bill's "Go" without a separate plan-review stop (same as auth-hardening) — cost if wrong: Bill reads the plan after the fact.
- Ruling 4: stripe pinned to 23.0.1 if ≥14 days old at install time, else 23.0.0 (23.1.0 is 7 days old) — supply-chain caution — cost if wrong: a slightly older SDK (no feature we need is missing).
- Ruling 5: period end read from items.data[0].current_period_end when absent on the subscription (newer Stripe API versions moved it) — cost if wrong: none (falls back either way).
- Ruling 6: the confirmation email is sent only while the subscription is `trialing` (a trial or a tester month); a returning customer (no trial, active at once) gets Stripe's receipt only — spec 6.1.5 ties it to a trial or tester month starting, and a retried send after day 15 would describe a trial already over — cost if wrong: returning customers get no confirmation from us.
- Ruling 7: accept @types/node (types-only optional peer of stripe, no install scripts, never loaded at runtime) despite being 8 days old — cost if wrong: negligible; revisit with an override if desired.
- review → Needs fixes. Important: (1) confirm still emitted for `active` (Ruling 6); (2) duplicate refund can be lost silently (cancel then refund, no retry; log has no org id; after-answer work on Cloud Run CPU throttling) — partly plan-mandated; (3) gateway money logic has no behavioural test.
- Ruling 8: a duplicate is recorded in a new column organizations.billing_duplicate_pending (sub id) inside the event transaction; cancelAndRefund on that recorded id is idempotent (cancel if live; refund the latest paid invoice unless already refunded) and clears the record on success; retried on every later webhook for that org and (Task 3) on the status call; the ENDED guard stays for anything not recorded — a lost refund would charge a customer twice — cost if wrong: one extra column and a retry path.
- Ruling 9: the webhook awaits runFollowUps before answering (still 200 if a follow-up fails; the event stays recorded and retries go through Ruling 8), instead of after the answer as the plan said — Cloud Run throttles CPU after a response, and the follow-ups are a few quick Stripe calls — cost if wrong: Stripe's delivery takes a little longer.
- Ruling 10: every follow-up failure log carries our numeric org id (no Stripe ids or objects) so Bill can find the charge.
- minor (deferred): @types/node 26.6.6 and undici-types 8.9.0 fresh in lockfile (types-only, no scripts) — Ruling 7 covers.
- fix round 1/5 (3 addressed, 0 open — Ruling 6 trialing-only confirm; recorded duplicates + retry + org-id logs; gateway behaviour tests; commits 76449d3..b232345)
- Ruling 11: start-up price check is bounded (~10 s) before listen; timeout = billing off with the reason logged; start-up logic lives in lib/billing/startup.js (testable) — cost if wrong: a slow Stripe at boot leaves billing off until the next restart.
- Ruling 12: CSV export = the whole organization's clients (every LO's), broker only, open when off or locked, formula cells neutralised — cost if wrong: none (it's the brokerage's own data).
- Ruling 13: GET /api/billing/status answers 200 { billing: { enabled: false } } when billing is off (card/portal stay 404) — the client calls status after every sign-in either way — cost if wrong: none.
- Ruling 14: the ARIVE feed and integrations routes stay ungated for a locked brokerage — the feed isn't a signed-in request (spec §6.2) and it only stores the brokerage's own loans — cost if wrong: a locked brokerage's book keeps updating.
- Ruling 15: an archived (inactive) Stripe price fails the start-up check; a recorded duplicate that becomes the org's own subscription is dropped from the pending list and never retried — sent back to the implementer as a pre-review fix — cost if wrong: none.
- Ruling 16: accept the implementer's narrowing — an adopted duplicate is dropped from the pending list only while it is live; an already-cancelled duplicate whose refund failed stays recorded and is still refunded — clearing it would lose a refund owed for a double charge — cost if wrong: none found.
